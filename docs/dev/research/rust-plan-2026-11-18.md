# Rust plan (2026-11-18)

The question: after the ONNX Runtime reader (branch `claude/ocr-engine-test`), is moving the app to Rust worth it,
and if so in what order. Planning only; no Rust code yet.

**Verdict.** Most of the size gain is already in hand without Rust. The ONNX-Python app is about 360 MB against
about 770 MB today. A Rust build would be about 150-185 MB, so roughly 200 MB less again, but it means porting about
38,700 lines, 70 % of them UI and 嘉宾 scenes the user judges by eye. Recommended:

1. Ship ONNX-Python first.
2. Then, if wanted, phase 1 below (a Rust OCR core called from Python), which pays for itself in size and CPU.
3. Decide on the full rewrite only after that, on whether the remaining 200 MB matters to her disk.

## 1. Size: today, ONNX-Python, Rust

Unpacked sizes of the Windows app folder. "Measured" means win_amd64 wheels pruned by `build/make_release.py`'s own
`Pruner`, or a published release asset. "Estimate" says what it rests on.

| Part | Today (Paddle) | ONNX-Python | Rust |
|---|---|---|---|
| Python runtime (embeddable 3.12) | ~22 (estimate: python.org is blocked here, typical embeddable size) | ~22 | 0 |
| Python packages | 613.5 (measured) | 231.2 (measured) | 0 |
| OCR engine | inside the packages (paddlepaddle 343) | inside (onnxruntime 50.5) | onnxruntime.dll 22.7 (measured, the DLL in the win wheel) |
| OpenCV (exact pixels) | inside (opencv-contrib 90) | inside (opencv-headless 74.6) | ~10-15, a minimal core+imgproc build linked in (estimate) |
| UI toolkit | inside (PySide6 48 + shiboken 3) | inside | Slint ~5 in the exe (estimate); Qt ~25-35 DLLs (estimate, PySide6's Qt DLLs) |
| Models | 95 (measured) | 95 | 95 |
| App code + sounds and pictures | ~10 (assets 7.6, love_scenes 0.7, code) | ~10 | ~8 (assets) + exe ~10-15 (estimate) |
| **Total** | **~770** (release v1.0.1: 324 MB zipped; 770 from the brief) | **~360** | **~150-185** |

- The models (95 MB, 74 of it PP-OCRv6_medium_rec) become the biggest part of a Rust build. Smaller models would
  change accuracy, which the user ruled out.
- A cheaper middle step stays in Python: a minimal OpenCV build (core+imgproc) instead of opencv-headless would take
  ONNX-Python from ~360 to ~300 MB. It is still OpenCV, so it gives the same pixels.

## 3. UI toolkit

Needs: the Claude-style 设置 (a catalog on the left, rows with dropdowns), light and dark themes, dialogs that fit
672 px, Chinese text, a tray icon, global hotkeys, a click-through on-game overlay, and per-pixel scenes at < 20 ms.

| Option | Fit | Against |
|---|---|---|
| **Slint (recommended)** | One native exe, small, low RAM and CPU (her laptop), styled freely, so the look in CLAUDE.md can be copied; renders CJK with system fonts (Microsoft YaHei). Royalty-free licence for desktop apps | Young; no tray or overlay built in, so those use windows-rs directly (they are Win32 code today anyway) |
| Qt via cxx-qt | Closest to today's PySide6 Widgets | cxx-qt is QML-first (Widgets binding weak); a C++ build plus 25-35 MB of Qt DLLs; LGPL dynamic linking |
| egui | Simplest to write | Looks like a tool, not like Claude's settings; immediate mode redraws cost CPU beside the game |
| WinUI 3 via windows-rs | Native Windows look | Rust support immature; needs the Windows App SDK runtime installed |
| Tauri (HTML/CSS) | Easiest to match a web-like design | WebView2 uses ~100-150 MB RAM (she has 4-6 GB free with MuMu); overlay and scenes still native |

Recommendation: Slint for the windows, windows-rs for overlay, capture, hotkeys and tray. How it looks is the
user's call, after a mock-up page in phase 3.

(about 45-60) are the rewrite.

## 5. Risks, and what only the user decides

- **Exact OCR parity in Rust** needs OpenCV's own resize, warpPerspective, findContours and minAreaRect. They must be
  linked, not re-implemented. Clipper (pyclipper's library) has a Rust binding to the same C++ code.
- **Visual parity** of 16 scenes and the whole UI is judged by the user's eye, so expect several rounds per scene.
- **The updater** must move players on v1.0.1 to a different folder layout without losing their lists. One chance to
  get it right.
- **Windows-only testing:** this container is Linux. Phases 2-5 need the desktop (one agent at a time) or a Windows VM.
- **Cost:** 60-80 packages, plus testers and fixes, is weeks of agent time. The ONNX-Python step was a day.
- **Only the user decides:**
  - whether to go past phase 0 or 1 (is 200 MB worth it for her disk?)
  - how the new UI looks (the Slint mock-up)
  - each release
  - the budget

  Her free disk space is not recorded in this repo (docs/dev/research/test-pc-like-hers-2026-10-18.md has CPU and
  memory only); it decides how much the last 200 MB is worth.
