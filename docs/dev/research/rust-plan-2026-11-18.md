# Rust plan (2026-11-18)

The question: after the ONNX Runtime reader (branch `claude/ocr-engine-test`), is moving the app to Rust worth it,
and if so in what order. Planning only; no Rust code yet.

**Decision (the user, 2026-11-18).** One big release: the full Rust rewrite, shipped once. There is no
ONNX-Python release; the ONNX reader (`blacklist_detect/onnx_ocr.py`, 924/924 names identical to Paddle on 85 real
lobbies) is the reference that the Rust OCR must match. The rewrite takes the app from ~770 MB to ~150-185 MB. It
means porting ~38,700 lines, 70 % of them UI and 嘉宾 scenes judged by eye: weeks of agent work.

## 1. Size: today, ONNX-Python, Rust

Unpacked sizes of the Windows app folder. "Measured" means win_amd64 wheels pruned by `build/make_release.py`'s own
`Pruner`, or a published release asset. "Estimate" says what it rests on.

| Part | Today (Paddle) | ONNX-Python | Rust |
|---|---|---|---|
| Python runtime (embeddable 3.12) | ~22 (estimate: python.org is blocked here, typical embeddable size) | ~22 | 0 |
| Python packages | 613.5 (measured) | 231.2 (measured) | 0 |
| OCR engine | inside the packages (paddlepaddle 343) | inside (onnxruntime 50.5) | onnxruntime.dll 22.7 (measured, the DLL in the win wheel) |
| OpenCV (exact pixels) | inside (opencv-contrib 90) | inside (opencv-headless 74.6) | ~10-15, a minimal core+imgproc build linked in (estimate) |
| UI toolkit | inside (PySide6 48 + shiboken 3) | inside | Slint ~5 in the exe (estimate); Qt ~25-35 DLLs (estimate, PySide6's Qt DLLs) |
| Models | 95 (measured) | 95 | 95 |
| App code + sounds and pictures | ~10 (assets 7.6, love_scenes 0.7, code) | ~10 | ~8 (assets) + exe ~10-15 (estimate) |
| **Total** | **~770** (release v1.0.1: 324 MB zipped; 770 from the brief) | **~360** | **~150-185** |

- The models (95 MB, 74 of it PP-OCRv6_medium_rec) become the biggest part of a Rust build. Smaller models would
  change accuracy, which the user ruled out.
- A cheaper middle step stays in Python: a minimal OpenCV build (core+imgproc) instead of opencv-headless would take
  ONNX-Python from ~360 to ~300 MB. It is still OpenCV, so it gives the same pixels.

## 3. UI toolkit

Needs: the Claude-style 设置 (a catalog on the left, rows with dropdowns), light and dark themes, dialogs that fit
672 px, Chinese text, a tray icon, global hotkeys, a click-through on-game overlay, and per-pixel scenes at < 20 ms.

| Option | Fit | Against |
|---|---|---|
| **Slint (recommended)** | One native exe, small, low RAM and CPU (her laptop), styled freely, so the look in CLAUDE.md can be copied; renders CJK with system fonts (Microsoft YaHei). Royalty-free licence for desktop apps | Young; no tray or overlay built in, so those use windows-rs directly (they are Win32 code today anyway) |
| Qt via cxx-qt | Closest to today's PySide6 Widgets | cxx-qt is QML-first (Widgets binding weak); a C++ build plus 25-35 MB of Qt DLLs; LGPL dynamic linking |
| egui | Simplest to write | Looks like a tool, not like Claude's settings; immediate mode redraws cost CPU beside the game |
| WinUI 3 via windows-rs | Native Windows look | Rust support immature; needs the Windows App SDK runtime installed |
| Tauri (HTML/CSS) | Easiest to match a web-like design | WebView2 uses ~100-150 MB RAM (she has 4-6 GB free with MuMu); overlay and scenes still native |

Recommendation: Slint for the windows, windows-rs for overlay, capture, hotkeys and tray. How it looks is the
user's call, after a mock-up page in phase 3.

## 4. Milestones on one branch

- **Branch:** `feature/rust`, cut from `1.x`. `1.x` keeps getting player fixes; it is merged into `feature/rust` at
  each milestone, so the Rust app ports the current behaviour, not a stale one.
- **Code layout:** a Cargo workspace in `rust/`:
  - `ocr` (the reading)
  - `win` (capture, hotkeys, overlay)
  - `data` (lists, settings, backups, logs, updater)
  - `scenes`
  - `app` (Slint UI and the exe)
- **Parity proof:** a `pyo3` binding of `ocr` lets `tools/engine_bench.py` compare it with Python on the corpus.
- **One release at the end.** Before it goes to everyone, she runs a test build on her own laptop.

| Milestone | Contents | Proof | Packages |
|---|---|---|---|
| M1 OCR core | det and rec on ort plus linked OpenCV; layout, pipeline and match logic | engine_bench `rust` engine: names identical on all 85 frames, confidences within 1e-4; CPU per check ≤ the Python reader's | 6 |
| M2 Data | lists, settings, 嘉宾, import, backups and logs read and written in the Python app's exact formats; the updater | golden files written by Python read back and written byte for byte; a backup round trip | 5 |
| M3 Windows layer | GDI/WGC capture, global hotkeys, single instance, tray, autostart, 直播姬 mode, click-through overlay cards | live checks on Windows (the desktop, one agent at a time) | 7 |
| M4 App shell | Slint windows: lists, 设置 (catalog plus rows), dialogs (672 px rule), header pill panel, notices, light and dark | page-by-page screenshots against `tools/ui_shots.py`; the user looks at a mock-up first | 25-30 |
| M5 Scenes and sound | the 16 嘉宾 scenes (way chosen by the user, below), music, sound import and trim | each scene beside the Python one at full size over the sample lobby; frame time | 18-24 |
| M6 Switch-over | the last v1.x update installs the Rust app (the Launcher already starts the app); data carried over | update from v1.0.1 on a clean Windows 10 VM; lists, settings and backups kept | 3-4 |

About 65-75 packages in all.
- **Side by side:** M1 and M2 have no shared files and run together. M3 needs the desktop, one agent at a time. M4
  starts once M2's data types exist, and can spread over 4-6 agents (one page or dialog each). M5's scenes are
  independent of each other.

## 5. First wave (ready to launch on the user's go; no desktop needed)

Each package is about 35 implementer calls; hand back at about 40. All of them first cut `feature/rust` from `1.x`
(W1-a does it; the others branch from it once it is pushed). Golden data comes from the Python code itself, written
by a small script in `tools/` inside each package.

- **W1-a Workspace and det path.**
  - Build: create `rust/` (Cargo workspace; crates `ocr` and `data` empty but building) and port onnx_ocr's
    detection side, all with ort and the `opencv` crate (core + imgproc): det_resize, normalize, db_boxes (Clipper
    through a binding of the same C++ library pyclipper uses), sort_boxes, crop_by_polys.
  - Test: golden boxes and crops from Python on the fixture and 10 corpus frames, bit for bit.
- **W1-b Rec path.**
  - Build: TextRecognizer: resize_norm, batch padding exactly as the Python batches it, CTC with the dictionary from
    inference.yml; the session settings (threads from the same rule as `paths.ocr_threads`, denormals as zero, no
    spinning).
  - Test: golden texts and scores from Python on 200 name strips cut from the corpus, scores within 1e-6.
- **W1-c Layout and match.**
  - Build: port layout.py (find_anchor, countdown, ready, name boxes) and match.py as pure functions over lines read.
  - Test: golden anchors and matches from Python on every corpus frame's lines, saved as JSON.
- **W1-d Data formats.**
  - Build: port storage.py's reading and writing of the lists, settings and backups.
  - Test: round trips on files written by the Python app (a data folder of its own; never the user's).
- **Wave 2 (after W1-a/b):**
  - W2-a: the pyo3 binding and a `rust` engine in engine_bench, run on the corpus.
  - W2-b: the pipeline glue (check_frames with the lobby spot).
  - M3 spikes on the desktop: the click-through overlay and, if the user picks shaders, one GPU scene.

## 6. Risks, and what only the user decides

- **Exact OCR parity:** needs OpenCV's own resize, warpPerspective, findContours and minAreaRect. They must be linked,
  not re-implemented. Clipper is bound to the same C++ code.
- **Visual parity** of the UI and 16 scenes is judged by the user's eye, so expect several rounds.
- **The one-shot switch-over:** players on v1.0.1 move to a new folder layout by one update. A test build on her
  laptop comes first.
- **Windows-only parts** (M3, the scene spike, M6) need the desktop or a Windows VM; this container is Linux.
- **Cost:** 65-75 packages, plus testers and fixes.
- **Only the user decides:**
  - the scene way
  - the look of the new UI (a mock-up)
  - when to start (the go for wave 1)
  - the final release

  Her free disk space is not recorded in this repo.
