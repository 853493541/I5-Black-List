# The friend's app froze in the tray (2026-10-17), and the evidence net (2026-10-18)

From her 导出日志 of 2026-10-18 (v1.0.0 lines; older ones as reference) and the code at c235e74. Names in her logs are
never quoted here.

## What happened

- **The run.** It started at 13:28:40 with 直播模式 on and 直播姬 closed. It went to the tray at 13:34:25 and logged its
  last line at 13:36:05. That line is the 直播画面 mirror refitting as the game's window disappeared: `follow()`,
  ui_stream.py:389-425.
- **It really froze** (HIGH). The 30-minute update check (`UPDATE_EVERY_MS`, ui.py:236) ran at 13:28:43; the next one,
  due at 13:58:43, never ran. In her healthy evening run, the same check logged every 30 minutes. So the main (Qt)
  thread stopped between 13:36:05 and 13:58:43.
- **How it ended.** At 17:07:18 the next start found the process alive with its pipe silent. `single.settle` tests only
  the pipe, which the main thread serves, so a lost tray icon alone would not explain it. It ended the process.
- **It happened once before.** 10-14 on v0.9.0: tray, 直播模式 on, right after 直播姬 closed.
- **Not the crash.log entries.** Her crash.log entries cite line numbers that do not match v1.0.0, so they come from
  older builds (MED).

## What it is not, and what it may be

- **The tray path is ruled out, by reading and by running.**
  - Every main-thread job there uses non-blocking Win32 calls and local file reads: the 3 s 直播姬 follow, the 2 s
    stream-setup check, the 45 ms mirror step, the 3 s system follow.
  - A reproduction ran it offscreen for 75 s: the game window vanished at 6 s, the scene file changed, broke or stayed
    locked every second, and the update check ran every 5 s. The main thread never stalled: 150 beats, 25 follows,
    38 setup checks, 1,594 mirror steps.
- **Hypotheses left, none proven:**
  - A native block on the GUI thread while hidden: Qt or the graphics driver during a lock, monitor-off or session
    change, with the translucent always-on-top mirror window at the screen's edge (MED-LOW).
  - A thread holding the GIL in a C call (LOW-MED).
  - The PC asleep the whole time (LOW: after waking, the overdue timer and the pipe would have answered before 17:07).
- **Today's code** still has the same tray code and had no watchdog until this branch.

## The evidence net (branch fix/freeze-evidence)

- **Main-thread watchdog** (`logs.watch_main_thread`, armed in `run_app` only).
  - A main-thread timer re-arms faulthandler every 2 s. If the thread stops for 30 s, crash.log gets every thread's
    Python stack ("Timeout (0:00:30)!").
  - A watchdog thread logs "Main thread not answering for N s (since HH:MM:SS)" after 10 s, and "answering again" if
    it recovers.
  - A gap longer than 20 s in the watchdog's own clock counts as the PC sleeping: no alarm.
- **Tray heartbeat.** "Tray: alive." once an hour while hidden, so a freeze is known to within the hour.
- **Stuck copy dumped before it is ended.** The next start writes `logs/stuck-<pid>.dmp` (thread stacks only, native
  ones included; the newest 3 are kept), then ends the copy. The warning now says only what was tested: its pipe did
  not answer.
- **Export.** 导出日志 carries the dumps, compressed into the same one text file; `diagnostics.dumps_in` reads them back.
  Her Windows account name is replaced in the dump byte for byte, as the text logs already replace it.
- **Tests:** tests/test_logs.py, tests/test_single.py, tests/test_diagnostics.py.

## Open

- **A false crash.log entry after sleep.** faulthandler's own timer may still write a Timeout dump to crash.log after
  the PC sleeps. How to read it: a Timeout dump with no "not answering" line beside it in app.log was a sleep.
- **Dump size.** No dump of a real Python + Qt process has been measured yet. One over 8 MB of text would be left out
  of the export, with a note, and kept in logs/.
- **The cause itself.** Her next export after a freeze, with the stacks above, is the next probe.
