# Why a check takes the whole CPU on the friend's laptop (2026-10-18)

The question: on the friend's PC (HP Victus 16, i5-11400H, 6 cores / 12 threads, see the master's memory) a hotkey check
makes the game lag and the CPU sit at 98-100 %. Why, and what can be done. Research only: nothing is built yet.

## What her log says (v1.0.0, 2026-10-17, 15 hotkey checks)

- A check takes 2.2-2.5 s: capture 0.05 s, find 0.10 s (the lobby where it was last time), read 2.1-2.3 s.
- During it the whole CPU is at 98-100 %, this app 67-72 % of it (about 8.4 of her 12 threads).
- The environment check, with the CPU to itself: 1.6 s a check, this app 96 %.

So the cost is the read: the 12 name strips through `PP-OCRv6_medium_rec` (`ocr_engine.OcrEngine.read_names`).

## Cause

PaddleOCR runs the model through oneDNN, whose OpenMP pool starts one thread per logical CPU: 12 on her laptop. The
app sets no thread count. `cpu_threads` (PaddleOCR's own setting, default 10) does not change it: 1, 2, 4 or 10 all
kept 8.5 cores busy. `OMP_NUM_THREADS`, read when OpenMP starts, does. `KMP_BLOCKTIME=0` does nothing.

With 12 threads on 12 CPUs and a game beside them, every layer waits for the threads the game pushed off a core: the
read gets slower (2.94 s under load against 1.09 s alone) and keeps every CPU busy while it waits.

## Measurements

v1.0.0's own runtime and models (the full zip unpacked to `dist/bench/`), the 12 name strips of
`tests/fixtures/reference-lobby.png`, on the user's PC (Ultra 9 285K) pinned to 12 CPUs to match her thread count.
Median of 8 reads after 2 warm-ups. "Same text" is against today's setting, which reads the reference lobby right.

| Setting | Read alone | CPU work | Cores busy | Same text |
|---|---|---|---|---|
| Today (no thread count) | 1.09 s | 9.3 s | 8.5 | 12/12 |
| `OMP_NUM_THREADS=6` | 0.73 s | 4.3 s | 5.8 | 12/12 |
| `OMP_NUM_THREADS=4` | 0.76 s | 3.0 s | 4.0 | 12/12 |
| `OMP_NUM_THREADS=2` | 1.31 s | 2.6 s | 2.0 | 12/12 |
| `OMP_NUM_THREADS=1` | 5.69 s | 5.6 s | 1.0 | 12/12 |
| MKL-DNN off | 1.69 s | 16.5 s | 9.7 | 12/12 |
| `PP-OCRv5_mobile_rec`, 4 threads | 0.20 s | 0.8 s | 4.0 | 11/12 |

With a stand-in game beside it (4 processes doing fixed small steps on the same 12 CPUs; "game speed" is how fast
their steps ran during the reads against before them):

| Setting | Read under load | Game speed during it |
|---|---|---|
| Today | 2.94 s | 83 % |
| Today, below-normal priority | 3.36 s | 93 % |
| 4 threads | 0.73 s | 94 % |
| 4 threads, below-normal priority | 0.70 s | 97 % |
| Mobile model, 4 threads | 0.20 s | 88 % |

The game loses about 0.5 s of its work per check today and about 0.02 s with 4 threads at below-normal priority.

## Does the thread cap cost anything? (whole checks)

Whole checks as the app runs them (`pipeline.check_rgb`), v1.0.0's runtime, the sample lobby (made-up names) at
1538 px wide on a 1920x1080 screen like her MuMu window. Each run loads the models, makes a first check (lobby search),
then 6 checks; the median is shown. The thread count is set from outside, before Paddle loads, as the fix would.

| CPUs (pinned) | Today | With the cap |
|---|---|---|
| 12, alone, 2 runs | 1.33 / 1.36 s, 8.5 cores busy | 4 threads: 0.96 / 0.99 s, 4.0 cores busy |
| 12, with the stand-in game, 2 runs | 3.22 / 4.62 s, game speed 76 / 74 % | 4 threads: 0.85 / 0.95 s, game speed 94 / 103 % |
| 6, alone | 2.61 s | 4 threads: 0.99 s |
| 4, alone | 3.62 s | 2 threads: 2.48 s |
| 24, alone | 0.76 s | 4 threads: 1.29 s (one run) |
| First check after start, 12 CPUs | 2.08 / 2.23 s | 1.47 / 1.37 s |
| Model load, all runs | 3.2-7.9 s | 3.2-5.9 s |

- On PCs like hers (4-12 CPUs) the cap was faster in every run, alone and beside a game. Under load today's setting also
  slows the lobby search (a 3.22 s check of which 1.65 s is the read); with the cap the check is the read.
- The only slower case is a big PC with nothing else running (24 CPUs: 0.76 to 1.29 s). That PC runs the app fine
  either way; if it ever matters, half the CPUs up to 8 is the next setting to measure.
- This PC's CPUs 0-11 are 4 fast and 8 efficiency cores; her laptop has 6 equal cores with hyperthreading. Her next log
  (each check logs its time and CPU) is the confirmation.
- The PC was 21-79 % busy with other work before a run; settings were run alternately so both saw the same load.

Accuracy: 72 whole screens, each searched fresh: both lobbies (reference and sample) x 6 window widths (960-1920 px on
a 1920x1080 screen) x 3 brightness levels (0.85, 1.0, 1.15) x PNG or JPEG 75. Against today's setting, 4 threads and 2
threads read 0 of the 864 names differently (shown name, raw text and unclear mark), confidence equal to 6 decimals,
and the same lobby found, countdown and ready count on all 72 screens. All three read 854 of 864 names as the tests
expect; the 10 misses are the same names on the same 8 hard screens (small window, darker or brighter, JPEG).

Bug risk: too few threads is the one danger (1 thread reads 5x slower, and an inherited `OMP_NUM_THREADS=1` once made
update restarts 3-14x slower), so the cap never goes below 2. Programs the app starts do not get it: `paths.child_env`
strips it.

## The small model is not safe yet

`PP-OCRv5_mobile_rec` misread one of the 12 reference names badly (2 of its 3 characters). It was its least sure read
(0.70), but another name at 0.80 was right, so 12 names cannot set a cut-off for re-reading only unsure names with the
medium model. That needs more real lobbies than the one in `tests/fixtures/`.

## Recommended fix (not built)

1. `__main__`: before Paddle loads, set `OMP_NUM_THREADS` for this process to 4 (2 on a PC with 4 or fewer cores).
   `paths.child_env` already keeps it out of programs the app starts.
2. Below-normal priority only while the OCR runs (`psutil.Process().nice`), back to normal before the marks are drawn.
3. Keep `PP-OCRv6_medium_rec`.

Expected on her laptop: a read using about a third of the CPU instead of 70 %, no slower and likely faster. Her laptop
is not this PC (6 cores with hyperthreading against 24 cores without), so this is an estimate until her next log,
which already records each check's time and CPU.

## Later, larger options

- Run the OCR on a graphics chip (her RTX 3050 or the idle Intel UHD) through ONNX Runtime with DirectML: the CPU would
  hardly be used, but it is a new dependency and the models must be converted and checked.
- A small first pass with the medium model only for unsure names, once there are enough real lobbies to test it.
- Auto mode: the thread cap cuts each glance's CPU work too; skipping glances when the screen has not changed is
  already there (`pipeline.same_band`).
